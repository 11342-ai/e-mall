秒杀防刷体系 — 补全多层防护

现状 :
    目前唯一的"防刷"机制是 Lua 脚本的 重复购买检测 （ SETNX skill:user:{uid}:{pid} ）。

缺少以下防护：
    - 接口级限流（无任何限流中间件）
    - 用户维度的请求频率控制
    - IP 黑名单 / 风控
    - 验证码机制
    - 请求签名校验
    - 用户标记无 TTL， 导致 Redis 内存泄漏

1. 接口级限流
    合理

    - 秒杀接口是系统最高频入口，典型的 CC 攻击/脚本刷单目标
    - Gin 生态有成熟的限流方案（token bucket / sliding window），可以做 middleware 挂载到特定路由
    - 不破坏任何现有结构，在 middleware/ 下加一个文件，在 routes/router.go 中对 flash_sale/skill 单独挂载即可

    推荐做法： 基于 github.com/juju/ratelimit + Redis 做分布式令牌桶，支持单机和集群部署。

2. 用户维度的请求频率控制 
    合理

    - 正常用户手动点击，1 秒内最多 1-2 次
    - 恶意脚本可以在 1 秒内刷几百次，虽然 Lua 脚本的防重复购买能拦住后续请求，但每次请求都走到 Redis Eval 也是资源浪费
    - 在 middleware 层提前拦截高频用户，可以把无效请求挡在业务逻辑之外
    
    推荐做法： 与机制 1 合并实现——一个统一的限流 middleware，支持按 {路由 + 用户ID} 和 {路由 + IP} 两个维度分别做计数器（Redis + 滑动窗口）。

3. IP 黑名单 / 风控 
    中等合理

    合理的一面：
        - 对连续失败（返回 -1 重复秒杀、 -2 已售罄）的 IP 做短时间封禁是有意义的
    
    不合理的一面：
        - 秒杀场景下大量正常用户在同一个 NAT 出口（公司/学校 WiFi），按 IP 限流会误伤严重
        - IP 可以轻易通过代理更换
        - IP 黑名单更适合在网关/CDN/WAF 层处理，应用层做效果有限
    
    建议： 做轻量版——在 Redis 中记录 {IP}:{秒杀失败次数} （TTL 5 分钟），超过阈值（如 20 次）拒绝请求。不作为主要防刷手段，仅做辅助。

4. 验证码机制 
    当前阶段不合理
    为什么不合理：
        - 秒杀是强时效场景 ，用户端加验证码会摧毁转化率——等用户输完验证码，库存早没了
        - 验证码只防初级脚本，专业黄牛用打码平台可以直接绕过，成本极低
        - 项目当前无验证码相关基础设施（无配置、无服务调用），集成成本高
        - 更有效的替代方案： 前端做行为分析 （按钮点击间隔、页面停留时间）+ 后端频率控制 ，效果远好于验证码
    如果有强烈需求： 建议只在秒杀开始前的 商品详情页 引入验证码/滑块，而不是在 提交秒杀请求 时引入。

5. 请求签名校验 
    价值有限，暂缓

    合理的一面：
        - 可以防止参数篡改和重放攻击
    
    不合理的一面：
        - 项目已在 JWT 鉴权保护下，用户身份可信任
        - 核心参数（ product_id ）在后端有缓存校验和数据库兜底，参数篡改无意义
        - 防重放： address_id 和 key 已经是请求的唯一标识组合
        - 签名校验增加前后端复杂度（客户端需要签名算法、密钥分发），收益在秒杀场景下不高
    
    建议： 如果要做，等有明确的重放攻击证据再引入。当前优先级很低。

6. 用户标记无 TTL → Redis 内存泄漏 
    必须修，高优先级 BUG

    不加 TTL 导致的后果：
    - 假设一次秒杀活动有 50 万用户参与，Redis 中新增 50 万个 skill:user:* key
    - 这些 key 永远不删除 ，占用的内存只增不减
    - 每周搞几次活动，Redis 内存持续增长，最终 OOM
    - 线上事故级别的风险
